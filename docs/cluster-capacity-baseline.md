# 集群容量基线

> 文档信息
>
> - 日期：2026-07-29
> - 主机：Apple M4，darwin/arm64
> - 范围：一致性哈希微基准与本机五节点真实进程基线
> - 结论：本机结果证明门禁有效，但不替代目标生产规格容量签字

## 1. 发现和修复

原配置每个物理节点只有 20 个虚拟节点。对 10 万个稳定 Topic 采样：

| 拓扑 | 最少 Topic | 最多 Topic | 最多/最少 |
| --- | ---: | ---: | ---: |
| 3 节点 | 23,335 | 46,486 | 1.99 |
| 5 节点 | 11,652 | 26,062 | 2.24 |

这种倾斜会让最忙节点提前耗尽 CPU、数据库写入和 Lane 容量。实现已把生产 Ring 的虚拟节点数提高到 256，并将默认 CRC32 Topic 查询改为零堆分配的等价字符串实现。

Ring 映射属于集群协议的一部分，因此本次修改把集群协议基线提升为版本 2，且不宣称兼容使用旧 20 副本 Ring 的预览版本 1。项目尚未发布生产集群版；后续任何 Ring 算法或副本数修改都必须再次提升协议版本，并提供明确迁移方案。

修改后固定测试样本：

| 拓扑 | 节点分布 | 最大值相对均值偏差 |
| --- | --- | ---: |
| 3 节点 | 33,423 / 30,884 / 35,693 | 7.08% |
| 5 节点 | 18,207 / 20,573 / 20,523 / 21,403 / 19,294 | 8.97% |

自动化测试要求每个节点与均值的偏差不超过 20%。3→5 扩容时 40.70% 的 Topic 迁往两个新节点，没有 Topic 在已有节点之间无效搬迁；移除第三个节点时只迁移该节点原有的 35.69% Topic。

## 2. Owner 查询微基准

命令：

```bash
go test ./internal/server -run '^$' \
  -bench 'BenchmarkClusterTopicOwner(3|5)Nodes' \
  -benchtime=2s -count=3
```

结果：

| 拓扑 | 延迟范围 | 堆分配 |
| --- | ---: | ---: |
| 3 节点 | 29.57～35.69 ns/op | 0 B/op，0 allocs/op |
| 5 节点 | 34.19～38.47 ns/op | 0 B/op，0 allocs/op |

微基准只测 Ring 查询，不包含 gRPC、TLS、序列化、数据库事务或 Fanout，因此不能用于推导消息 QPS。

## 3. 五节点真实进程基线

`scripts/test-cluster-process.sh` 在隔离环境启动三节点 etcd mTLS、MySQL 和
五个独立 IM 进程，执行 3→5 后测得：

| 场景 | 本机实测 | 发布门限 |
| --- | ---: | ---: |
| 热点 Topic | 32 接收者 × 300 条消息，共 9600 次网络投递 | 全部投递 |
| 发布 ACK p99 | 31.68ms | ≤300ms |
| 在线投递 p99 | 31.77ms | ≤500ms |
| 重连突发 | 256 路全部成功，p95 123.35ms | 无级联失败 |
| Owner SIGKILL | RTO 4s，ACK 历史保留，seq 继续递增 | ≤15s，RPO=0 |

原始结果保存在 `test-results/cluster-certification-latest.md`。脚本把 p99 门限
写成硬断言，超过即返回非零，不允许只打印日志后继续发布；报告同时记录被测
二进制 SHA-256 和工作区是否包含未提交变更，避免只凭 Git commit 误认测试对象。

## 4. 目标环境仍需签字的容量

CLUSTER-012 必须在固定 Linux 生产规格上记录：

- 3/5 节点长连接上限、目标登录恢复速率和跨可用区重连风暴。
- 生产 PostgreSQL/MySQL 连接池、事务 p95/p99 和真实主备切换。
- 1 KiB、64 KiB、4 MiB 消息的发布 ACK 和在线投递 p95/p99。
- 普通群、万人群和广播频道的 Fanout CPU、内存、网卡及队列水位。
- mTLS Lane 在目标网络延迟、丢包和节点故障下的吞吐退化。

这些结果必须与 72 小时报告、硬件规格和监控快照一起评审。
